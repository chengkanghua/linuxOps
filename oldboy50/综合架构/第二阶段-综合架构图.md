## 一、先搞懂几个核心概念

| 概念 | 含义 | 通俗类比 |
| --- | --- | --- |
| **项目** | 一次性、有明确目标和交付物的工作 | 搭一套监控系统（做完就结束） |
| **架构** | 系统的整体结构设计 | 楼的图纸，决定能扛多少压力 |
| **集群** | 多台服务器一起干同一件事 | 一群人分工干活，提效又可靠 |
| **高可用** | 通过冗余避免单点故障，系统尽量不中断 | 双机热备：主节点干活，备节点待命，主挂了备自动接管 |

**常见架构形态**
- **单体架构**：所有功能都在一个程序里，适合小公司初期。
- **微服务架构**：把大系统拆成多个独立的小服务，适合大公司。

**运维常见集群**
- **Nginx 集群**：多台 Nginx 一起处理网页请求。
- **MySQL 集群**：多台 MySQL 一起存数据，保证数据不丢。
- **Redis 集群**：多台 Redis 一起缓存数据，提高访问速度。

## 二、用户访问网站的完整流程

1. 浏览器输入 `oldboyedu.com` 并回车。
2. 进行 **DNS 解析**，拿到真实公网 IP。
3. 通过 **TCP 三次握手** 与公网 IP 建立连接。
4. 连接经 公网 → 路由器 → 交换机 → 抵达前端**防火墙**。
5. 防火墙按规则判定：恶意连接拒绝，正常连接放行。
6. 防火墙把连接发给**负载均衡器**，它根据请求内容下发给对应 Web 服务器。
7. Web 服务收到请求后判断：
   - 请求图片/附件 → 交给**存储服务**；
   - 请求文章内容 → 先查**缓存服务器**；缓存没有再去**数据库**。
   - 数据库查完返回 Web 服务，同时写一份给缓存（下次直接命中）。
8. 数据沿 数据库 → Web → 负载均衡 → 用户 原路返回。

> 一句话：请求自上而下经过「防火墙 → 负载均衡 → Web → 缓存/存储/数据库」，响应再原路返回。

## 三、管理人员维护流程

1. 通过公网 **VPN（隧道）** 连接内网，方便批量管理主机、备份重要文件。
2. 通过公网连接**监控服务器**（也可用其他方式），随时掌握集群状态。

## 四、网站业务五层架构（运维标准版）

请求从上往下流动，每层职责单一：

| 层级（从上到下） | 核心职责 | 常用技术栈 | 运维核心工作 |
| --- | --- | --- | --- |
| **1. 接入层**（负载均衡/反向代理） | 统一流量入口、请求分发、SSL 卸载、限流 | Nginx、LVS、HAProxy、Keepalived | 高可用集群、负载均衡策略、SSL 证书管理 |
| **2. Web 应用层** | 处理核心业务逻辑（系统大脑） | Tomcat、SpringBoot、Node.js、Go | 应用集群、扩缩容、日志收集、JVM 调优 |
| **3. 存储服务层** | 存非结构化数据（文件/图片/视频） | MinIO、FastDFS、OSS、NAS | 分布式存储集群、备份、容量监控 |
| **4. 数据缓存层** | 缓存热点数据，降低数据库压力 | Redis、Memcached | 主从复制、集群、持久化、内存优化 |
| **5. 数据持久化层** | 存结构化核心业务数据 | MySQL、PostgreSQL、MongoDB | 主从复制、双机热备、分库分表、备份恢复 |

**分层核心优势**
1. **职责单一**：每层只做一件事，便于定位和分工。
2. **独立扩展**：哪层压力大就加哪层（图片多就扩存储层）。
3. **故障隔离**：缓存挂了不影响数据库，存储挂了不影响核心业务。
4. **技术选型灵活**：不同层用最适合的技术栈。

## 五、Linux 运维最常见的 8 种架构（从小到大）

> 按**业务规模从小到大**排序，覆盖从个人博客到千万级互联网公司的主流架构。看完就知道每个阶段该掌握什么。

### 一、单服务器架构（入门级，必掌握）
- **适用场景**：个人博客、测试环境、小公司初期（日活 < 1000）、内部工具。
- **核心特点**：所有服务跑在一台 Linux 上，成本最低、运维最简单。

**核心组件**
```
用户 → Nginx（静态+反向代理） → Tomcat/Node.js（业务） → MySQL（数据库）
```

**运维核心工作**
1. 系统初始化、安全加固（防火墙、SSH 配置）。
2. 一键部署 LNMP/LAMP 环境。
3. MySQL 每日自动备份。
4. 基础监控（CPU、内存、磁盘、进程）。
5. 日志切割和轮转。

**优缺点**：✅ 部署快、成本低、无分布式复杂度 ｜ ❌ 单点故障、性能上限低、无法扩容。

---

### 二、经典三层集群架构（运维标配，必精通）
- **适用场景**：中小公司官网、电商店铺、内部系统（日活 1 万 ~ 10 万）。
- **核心特点**：三层分离，每层都可独立集群化，解决单服务器性能和单点问题。

**核心组件**
```
用户 → 接入层（Nginx 双机热备） → 业务层（Tomcat 集群） → 数据层（MySQL 主从）
```

**运维核心工作**
1. Nginx + Keepalived 双机热备，接入层高可用。
2. Nginx 负载均衡，分发到多台 Tomcat。
3. MySQL 主从复制，实现读写分离。
4. 统一日志收集（ELK）。
5. 全栈监控（Zabbix/Prometheus）。
6. 自动化发布脚本（Shell/Ansible）。

**优缺点**：✅ 无单点故障、可独立扩容、运维成本适中 ｜ ❌ 数据库主库单点、无缓存、业务层臃肿。

---

### 三、四层架构（加缓存层）
- **适用场景**：日活 10 万 ~ 50 万，数据库压力大、热点数据多。
- **核心特点**：三层基础上加缓存层，90% 热点请求直接命中缓存，大幅降低数据库压力。

**核心组件**
```
用户 → 接入层 → 业务层 → 缓存层（Redis） → 数据层（MySQL 主从）
```

**运维核心工作**
1. Redis 主从 + 哨兵，缓存高可用。
2. Redis 持久化策略（RDB + AOF）。
3. 缓存穿透 / 击穿 / 雪崩的防护。
4. Redis 内存监控与优化。
5. 数据库读写分离。

**优缺点**：✅ 数据库压力降 90%、响应提速 ｜ ❌ 增加缓存运维复杂度、有数据一致性问题。

---

### 四、五层架构（加分布式存储层）
- **适用场景**：大量图片/视频/文件的业务（电商、短视频、网盘）。
- **核心特点**：非结构化数据从数据库分离，交给分布式存储系统管理。

**核心组件**
```
用户 → 接入层 → 业务层 → 缓存层 → 分布式存储层（MinIO/FastDFS） → 数据库层
```

**运维核心工作**
1. 部署 MinIO/FastDFS 分布式存储集群。
2. 存储节点容量监控与自动扩容。
3. 数据备份和异地容灾。
4. CDN 加速配置。
5. 大文件上传/下载优化。

---

### 五、微服务架构（中大型公司标准）
- **适用场景**：日活 50 万以上，业务复杂、团队规模大。
- **核心特点**：单体业务拆成多个独立微服务，每个可独立开发、部署、扩容。

**核心组件**
```
用户 → 网关层（Spring Cloud Gateway/Nginx） → 微服务集群 → 缓存层 → 消息队列 → 数据库集群
```

**运维核心工作**
1. 容器化部署（Docker）。
2. 容器编排（Kubernetes/K8s）。
3. 服务注册与发现（Nacos/Consul）。
4. 消息队列运维（RocketMQ/Kafka）。
5. 分布式链路追踪（SkyWalking/Jaeger）。
6. CI/CD 流水线（Jenkins/GitLab CI）。

**优缺点**：✅ 服务解耦、独立扩容、分工明确 ｜ ❌ 运维复杂度极高、需掌握大量分布式技术。

---

### 六、高可用架构（运维核心能力）
- **适用场景**：不能中断的核心业务（支付、交易、金融）。
- **核心特点**：冗余设计消除所有单点故障，保证 99.99% 以上可用性。

**常见高可用方案**

| 层级 | 高可用方案 | 常用软件 |
| --- | --- | --- |
| 接入层 | 双机热备 + DNS 轮询 | Keepalived、LVS |
| 业务层 | 集群 + 负载均衡 | Nginx、K8s |
| 缓存层 | 主从 + 哨兵/集群 | Redis Sentinel、Redis Cluster |
| 数据库层 | 主从 + MGR / 分库分表 | MySQL MGR、TiDB |
| 存储层 | 多副本 + 异地容灾 | MinIO、Ceph |

**运维核心工作**
1. 心跳检测和自动切换。
2. 故障演练和灾备演练。
3. 容量规划和冗余设计。
4. 全链路压测。

---

### 七、大数据架构
- **适用场景**：海量数据存储分析（日志分析、用户行为、推荐系统）。
- **核心特点**：分布式存储 + 计算，处理 TB/PB 级数据。

**核心组件**
- 分布式存储：HDFS
- 分布式计算：Spark、Flink
- 数据仓库：Hive、ClickHouse
- 消息队列：Kafka

**运维核心工作**
1. Hadoop/Spark 集群部署与维护。
2. 集群性能调优。
3. 数据备份和安全。
4. 资源调度和管理。

---

### 八、监控告警架构（所有架构的基础）
- **适用场景**：所有生产环境。
- **核心特点**：全栈监控，提前发现问题、快速定位故障。

**主流监控方案**
- 基础监控：Prometheus + Grafana（推荐）、Zabbix
- 日志监控：ELK、Loki
- 链路监控：SkyWalking、Pinpoint
- 告警通知：钉钉、企业微信、邮件

**运维核心工作**
1. 监控指标全覆盖（服务器、中间件、应用、数据库）。
2. 告警规则优化（避免告警风暴）。
3. 监控面板定制。
4. 故障自动恢复脚本。

## 六、基础环境准备（虚拟机规划）

### 1. 克隆方式
- **链接克隆**：依赖母体，省空间。
- **完整克隆**：完全复制一份，占用独立磁盘空间。

> 克隆前先给虚拟机添加**内网卡**（第二块网卡，用于内部通信）。

![添加内网卡](img/%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-%E7%BB%BC%E5%90%88%E6%9E%B6%E6%9E%84%E5%9B%BE-02.png)

**新建内网卡（eth1）**
```bash
# 新增一张内网网卡连接（相当于手写 ifcfg-eth1）
nmcli connection add con-name eth1 ifname eth1 type ethernet \
  ipv4.addresses 172.16.1.222/24 autoconnect yes ipv4.method manual

# 参数说明
connection add   新增一条连接
con-name         连接名称（eth1）
ifname eth1      绑定的物理网卡
type ethernet    以太网类型
ipv4.addresses   IP 地址/掩码
autoconnect      是否开机自启
ipv4.method manual   手动配置 IPv4
```

### 2. 克隆后必须做的操作
1. 修改主机名：`hostnamectl set-hostname backup`
2. 修改 IP：`sed -i 's#222#41#g' /etc/sysconfig/network-scripts/ifcfg-eth[01]`
3. 重启服务器。
4. 创建 Xshell 标签，测试连接是否成功。
5. 基于已克隆好的机器打快照。

![克隆步骤](img/%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-%E7%BB%BC%E5%90%88%E6%9E%B6%E6%9E%84%E5%9B%BE-03.png)
![克隆步骤](img/%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-%E7%BB%BC%E5%90%88%E6%9E%B6%E6%9E%84%E5%9B%BE-04.png)
![克隆步骤](img/%E7%AC%AC%E4%BA%8C%E9%98%B6%E6%AE%B5-%E7%BB%BC%E5%90%88%E6%9E%B6%E6%9E%84%E5%9B%BE-05.png)

```bash
# 修改主机名
hostnamectl set-hostname backup

# 修改网卡 IP（把 222 改成 41）
sed -i 's#222#41#g' /etc/sysconfig/network-scripts/ifcfg-eth[01]
nmcli connection reload        # 修改配置文件后重新加载
nmcli connection down eth1 && nmcli connection up eth1   # 重启 eth1 生效
nmcli connection down eth0 && nmcli connection up eth0   # 重启 eth0 生效

# 配置 EPEL 源（RHEL 7）
wget -O /etc/yum.repos.d/epel.repo http://mirrors.aliyun.com/repo/epel-7.repo

# 查看网卡状态
nmcli device
# DEVICE  TYPE      STATE    CONNECTION
# eth0    ethernet  连接的    eth0
# eth1    ethernet  连接的    eth1
```

## 七、常见面试题

1. **什么是集群？为什么要用集群？**
   多台服务器协同完成同一任务，目的是提高性能、可用性和扩展性，避免单点故障。

2. **单体架构和微服务架构的区别？各自适用场景？**
   单体所有功能在一个程序里，简单但难扩展；微服务按业务拆分，独立部署扩容，适合复杂大团队。小型项目用单体，大型项目用微服务。

3. **什么是高可用？如何实现？**
   通过冗余消除单点故障，保证系统不中断。常见手段：双机热备（Keepalived）、集群 + 负载均衡、主从复制、异地多活。

4. **请描述一次完整的用户访问网站流程。**
   见本文「用户访问网站流程」八步：DNS 解析 → TCP 握手 → 防火墙 → 负载均衡 → Web → 缓存/数据库 → 原路返回。

5. **五层架构每一层的作用是什么？**
   接入层（流量入口/负载均衡）、Web 层（业务逻辑）、存储层（文件/图片）、缓存层（热点数据）、持久化层（结构化数据）。

6. **为什么要在三层架构里加缓存层？会带来什么问题？**
   缓存能挡掉 90% 热点请求，极大减轻数据库压力；代价是增加运维复杂度，并引入数据一致性问题（需处理穿透/击穿/雪崩）。

7. **链接克隆和完整克隆的区别？**
   链接克隆依赖母体、省空间；完整克隆独立复制一份、占空间但互不影响。

8. **双网卡（公网 + 内网）的作用是什么？**
   公网网卡对外提供服务，内网网卡用于集群内部通信（数据同步、管理），内外分离更安全、带宽更可控。
