**<font style="color:blue;">【NAT模式工作原理】：</font>**

**一句话原理：** LB 当"中转员"，进出流量都经过它、由它改 IP。

**工作过程：**

1. 客户端把请求发给 VIP（也就是 LB）。
2. LB 按调度算法选一台 RS，把数据包的目标 IP/端口改成 RS 的 IP/端口，转发过去。
3. RS 的默认网关指向 LB，处理完后把响应交回 LB。
4. LB 把响应包的源 IP 改成 VIP，再发回客户端。

**记忆点：** 请求和响应都过 LB，地址被改写两次。

![1553346872026-06b29a83-af82-4d13-9189-d95810a8b07b.jpeg](img/%E6%9B%BE%E8%80%81%E6%B9%BF%E5%B8%A6%E4%BD%A0%E8%BD%BB%E6%9D%BE%E8%BF%87%E9%9D%A2%E8%AF%95-%E6%8A%80%E6%9C%AF%E7%AF%87-01.jpeg)￼

**<font style="color:blue;">【NAT模式优缺点】：</font>**

**优点：**

- LB 上只需 1 个公网 IP。
- 支持 IP 和端口转换，用户访问端口和 RS 实际端口可以不一致。

**缺点：**

- 请求、响应都要过 LB 改写，高并发时 LB 是瓶颈，一般最多带 10~20 台 RS。
- 所有 RS 的默认网关必须指向 LB 的内网地址。

***

**<font style="color:green;">【TUNNEL模式工作原理】：</font>**

**一句话原理：** LB 用 IP 隧道只转发请求，RS 把响应直接回给客户端，绕开 LB。

**工作过程：**

1. LB 把请求报文再封装一层（IP 隧道），发给 RS。
2. RS 解封拿到原请求，处理后直接把响应返回客户端（源 IP 仍是 VIP）。
3. LB 全程只处理入站请求，不碰响应。

**记忆点：** LB 只做入站请求转发；响应数据通常比请求大得多，集群吞吐可提升约 10 倍。

![1553346872061-3f69e191-a3a3-482b-842b-cded6f0e57f6.jpeg](img/%E6%9B%BE%E8%80%81%E6%B9%BF%E5%B8%A6%E4%BD%A0%E8%BD%BB%E6%9D%BE%E8%BF%87%E9%9D%A2%E8%AF%95-%E6%8A%80%E6%9C%AF%E7%AF%87-02.jpeg)￼

**<font style="color:green;">【TUNNEL模式优缺点】：</font>**

**优点：**

- LB 只转发请求，响应由 RS 直发，LB 不再是瓶颈，能带大量 RS。
- 走公网即可分发，支持跨地域。
- 大并发下吞吐高（约提升 10 倍）。

**缺点：**

- RS 必须有合法公网 IP。
- 要求 RS 支持 IP Tunneling（IP 封装）协议，基本只能用 Linux。

***

**<font style="color:purple;">【DR模式工作原理】：</font>**

**一句话原理：** LB 只把数据帧的目标 MAC 改成 RS 的 MAC，在局域网内转发；RS 直接把响应回给客户端。

**工作过程：**

1. LB 不动目标 IP/端口，也不做隧道封装，只把数据帧的目标 MAC 改成选中 RS 的 MAC，在局域网发出。
2. RS 收到帧，IP 层看到目标 IP 是 VIP。所以 RS 上要做两件事：在回环口 lo 绑定 VIP（否则不收这个包）；关闭 lo 的 ARP 响应做 ARP 抑制（否则多台 RS 的 lo 都应答 VIP 会冲突）。
3. RS 处理后直接把响应发回客户端，源 IP 仍是 VIP。

**记忆点：** 改的是 MAC 不是 IP；没有隧道开销，但 LB 和所有 RS 必须在同一个局域网。

![1553346872203-a7957bb1-93bd-461f-865d-386c1453ebe5.jpeg](img/%E6%9B%BE%E8%80%81%E6%B9%BF%E5%B8%A6%E4%BD%A0%E8%BD%BB%E6%9D%BE%E8%BF%87%E9%9D%A2%E8%AF%95-%E6%8A%80%E6%9C%AF%E7%AF%87-03.jpeg)￼

**<font style="color:purple;">【DR模式小结】：</font>**

1）通过在调度器LB上修改数据包的目的MAC地址实现转发。注意源地址仍然是CIP，目的地址仍然是VIP地址。

2）请求的报文经过调度器，而RS响应处理后的报文无需经过调度器LB，因此并发访问量大时使用效率很高（和NAT模式比）

3）因为DR模式是通过MAC地址改写机制实现转发，因此所有RS节点和调度器LB只能在一个局域网里面

4）RS主机需要绑定VIP地址在LO接口上，并且需要配置ARP抑制。

5）RS节点的默认网关不需要配置成LB，而是直接配置为上级路由的网关，能让RS直接出网就可以。

6）由于DR模式的调度器仅做MAC地址的改写，所以调度器LB就不能改写目标端口，那么RS服务器就得使用和VIP相同的端口提供服务。

***

**<font style="color:brown;">【FULLNAT模式工作原理】：</font>**

**一句话原理：** 进出包都过 LVS（类似 NAT），但 RS 和交换机零配置，还能跨 VLAN。

**关键：** 引入内网地址 LIP（local address），先做 CIP→VIP，再转成 LIP→RIP。LIP 和 RIP 都是 IDC 内网 IP，所以能跨 VLAN 通信，后端无需任何改动。

**<font style="color:brown;">【FULLNAT模式优缺点】：</font>**

**最大问题：** RS 拿不到真实用户 IP。

**解决办法 TOA：** 把客户端 IP 塞进 TCP Option 一起带给 RS；RS 上安装 toa 内核模块，从 TCP Option 中取出真实客户端 IP。

**<font style="color:brown;">【FULLNAT模式出现的原因】：</font>**

淘宝这种大规模场景下，官方 LVS 不够用，主要有 3 点：

1. 前面三种模式部署成本都偏高。
2. 相比商用负载均衡，LVS 没有抗 DDoS 能力。
3. 主备模式性能无法横向扩展，单个 VIP 流量太大时扛不住。

***

**HAproxy与LVS异同**

| 对比项 | LVS | HAProxy |
|---|---|---|
| 实现方式 | 基于 Linux 内核 | 基于第三方应用 |
| 工作层级 | 只做 4 层 | 4 层 + 7 层（TCP/HTTP） |
| 健康检查 | 方式单一 | 功能强，支持端口、URL、脚本 |
| 性能 | 高，接近硬件负载均衡 | 功能强，但整体性能低于 4 层 LVS |
| 共同点 | 都是软件负载均衡 | 都是软件负载均衡 |

**<font style="color:red;">综上所述，HAProxy和LVS各有优缺点，没有好坏之分，要选择哪个作为负载均衡器，要以实际的应用环境来决定。</font>**

**为什么使用nginx做负载均衡**

我们公司用 Nginx 做负载均衡，原因：

- web 本来就是 Nginx，技术栈统一，方便管理、容易做自动化。
- 1.9 版本后新增 stream 模块，也能做 4 层负载（以前只能做 7 层）。
- 还能配合 Lua 做前端 WAF，也能做文件缓存、模拟简易 CDN。

**记忆点（易考）：** stream 做 4 层只能轮询，后端多个域名共用 80 端口时分发会出错。

**web**

门户 web 用 Nginx + Tomcat 或 Nginx + PHP：

- Nginx 负责静态页面，Tomcat/PHP 负责动态页面、跑 Java/PHP 程序。
- Nginx 里配置 rewrite 做伪静态，URL 更友好，也利于缓存、提升效率。

*<u>伪静态范例:</u>*

```nginx
location / {
        root   /var/www/project;
        index  index.php index.html;
        if ( -f $request_filename/index.html ){
                 rewrite (.*) $1/index.html break;
        }
        if ( -f $request_filename/index.php ){
                rewrite (.*) $1/index.php;
        }
        if ( !-f $request_filename ){
                rewrite (.*) /index.php;
        }
}
```

*<u>有了事务的概念，事务的特性？</u>*

1. 原子性 Atomicity：一个事务里的操作要么全成功，要么全回滚，不会只做一半。
2. 一致性 Consistency：事务执行前后，数据库始终从一个合法状态变到另一个合法状态。
3. 隔离性 Isolation：多个事务并发执行时，彼此互不干扰。
4. 持久性 Durability：事务一旦提交，修改就永久保存，不会丢失。

`status:404` 搜索http状态码为404的日志

字段本身是否存在

`_exists_：http`：返回结果中需要有http字段

`_missing_：http`：不能含有http字段

3）通配符搜索

`?` 匹配单个字符

`*` 匹配0到多个字符

`?` `*` 不能用作第一个字符，例如：`?status` `*status`

4）正则搜索

es支持部分正则功能,性能较差

`domain:/adm?n.vantage(fx[prime]).com.cn/`

5）模糊搜索

`quikc~` `brwn~` `foks~`

`~`:在一个单词后面加上~启用模糊搜索，可以搜到一些拼写错误的单词

`first~` 这种也能匹配到 frist

还可以设置编辑距离（整数），指定需要多少相似度

`cromm~1` 会匹配到 from 和 chrome

默认2，越大越接近搜索的原始值，设置为1基本能搜到80%拼写错误的单词

6）近似搜索

在短语后面加上`~`，可以搜到被隔开或顺序不同的单词

`"where select"~5` 表示 select 和 where 中间可以隔着5个单词，可以搜到 select password from users where id=1

7）范围搜索

数值、时间、IP、字符串类型的字段，都可做范围查询。

`length:[100 TO 200]`

`sip:["172.24.20.110" TO "172.24.20.140"]`

`date:{"now-6h" TO "now"}`

`tag:{b TO e}` 搜索 b 到 e 之间的字符

`count:[10 TO *]`：`*` 表示该端不限制范围

`count:[1 TO 5}`：`[ ]` 表示包含端点，`{ }` 表示不包含端点，可混用；此例为 1 到 5，含 1、不含 5

可以简化成以下写法：

`age:>10`

`age:<=10`

`age:(>=10 AND <20)`

8）优先级

`quick^2 fox`

用 `^` 提高词语权重，默认为 1；写成 0~1 之间的小数则降低权重。

9）逻辑操作

`AND`

`OR`

`+`：搜索结果中必须包含此项

`-`：不能含有此项

`+apache -jakarta test aaa bbb`：结果中必须存在apache，不能有jakarta，剩余部分尽量都匹配到

10）分组

`(elasticsearch OR logstash) AND elasticsearch`

11）字段分组

`title:(+return +"pink panther")`

`host:(baidu OR qq OR google) AND host:(com OR cn)`

12）转义特殊字符

`+ - = && || > < ! ( ) { } [ ] ^ " ~ * ? : \ /`

以上字符当作值搜索的时候需要用\转义

`\(1\+1\)\=2`用来查询(1+1)=2

NAT的特性：

 1> 节点应该使用私有地址；

 2> 节点的网关的必须指向lvs；

 3> 节点IP和lvs服务器IP必须在同一网段内；

 4> 请求和响应的报文都得经过lvs服务器；在高负载场景中，lvs服务器很可能成为系统性能瓶颈；

LVS 不是一个软件。 部署lvs 安装 ipvsadm
